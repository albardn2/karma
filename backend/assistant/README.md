# Karma Assistant — spike

A chat assistant that answers questions about a company's Karma data and carries
out actions in it by calling Karma's own API **as the signed-in user**. Every
change needs the user's explicit approval. Local data only.

## Actions (writes)

- All write endpoints the user may call are available as tools (124; `location`
  writes are never offered). Turn them off with `--read-only`.
- **Nothing is written without approval.** Before every write the harness:
  1. validates the input against the endpoint's schema (unknown or wrong fields are
     rejected and the user is never asked to approve something that can't work);
  2. resolves every id to a name as the user, shows order lines and totals, and for
     an update shows a before → after diff against the current record;
  3. asks the user. Ordinary writes: `y`. **Money, stock movements and deletes**
     (payments, payouts, transactions, notes, invoices, prices, checkout,
     fulfil/unfulfil, cancel, zero-out, any DELETE…): type `CONFIRM`.
- The default confirm callback denies, so a caller with no way to ask (e.g. the
  eval) can never write. Writes cannot be issued from code execution.
- `created_by_uuid` is removed from every schema and input — the server records who
  acted. Each approved write carries `Idempotency-Key: assistant-<conversation>-<call>`.
- Verified live (local stack): create customer → `y` → created; delete it →
  `CONFIRM` → deleted; 1 SYP payment → declined → nothing written, model did not retry.

Design: `qa-reports/karma-assistant-design.md` (main checkout, not in git).

## How it works

```
question ─► Conversation (agent.py) ─► Provider (providers/) ─► Claude
                 ▲                                │ tool calls
                 │ results                        ▼
                 └──────── Executor (tools.py) ── KarmaClient (user's JWT) ─► Karma API
```

- **catalog.json** — every API route (auth, super-admin, account excluded) with its
  method, path, CRUD action, docstring and input schema from the Pydantic DTOs.
  Generated by `gen_catalog.py` from the Flask route table; regenerate after API changes.
- **tools.py** — turns catalog entries into tools, keeping only what the user's
  effective permissions allow (the API re-checks every call). Only READ endpoints
  are exposed; the executor refuses anything else even if a model names it.
- **query_data.py** — a harness tool for analysis: pages through a list endpoint as
  the user, then filters / groups / aggregates / sorts locally and returns only the
  result. Works with any model; runs no model-written code.
- **providers/** — one interface; `anthropic_provider.py` uses tool search (the ~140
  endpoint tools are loaded on demand), prompt caching, effort, refusal fallback and,
  with `--code`, programmatic tool calling (`fetch_all` from code execution).
- **registry.py** — selectable models with prices and capabilities. The super-admin
  dropdown (phase 1) will pick an `id` from here.

## In the web app

A corner button (bottom-right) opens a chat panel on every signed-in page
(`frontend/client/src/components/assistant/`). Answers stream in; each write shows
as a confirmation card with Approve / Cancel (money, stock and deletes need
`CONFIRM` typed — enforced by the service, not just the browser). The widget only
renders when `VITE_ASSISTANT_URL` is set, so builds without it are unchanged.

```bash
# 1. the assistant service (port 5077; 5050 is often taken on macOS)
cd backend && ASSISTANT_PORT=5077 ANTHROPIC_API_KEY=... \
  uv run --no-project --python 3.12 --with-requirements assistant/requirements.txt python -m assistant.server

# 2. this branch's web app on :3001, reusing the local frontend image's node_modules
docker run --rm --name karma-assistant-web -p 3001:5000 \
  -v "$(pwd)/frontend":/app -v /app/node_modules -e NODE_ENV=development \
  -e VITE_API_BASE_URL=http://localhost:5000 -e VITE_ASSISTANT_URL=http://localhost:5077 \
  karma-frontend:latest
```

### Voice

The mic button next to the message box starts voice mode: speak a question, hear
the answer, and it listens again until you end it (✕). The bar shows the live
transcript; tap the big button to interrupt the reply or to talk after a pause;
`EN / عربي` switches the listening language (defaults to the app language). The
answer is spoken sentence by sentence while it streams (tables, ids and markdown
are skipped; the Arabic or English voice is picked per sentence). The written
conversation is kept in the chat; spoken questions show a mic icon.

With `voice: true` on a message, the model is told the user is listening (an
appended context message, once per switch): short spoken-style answers, numbers
said naturally, "details are in the chat" for charts/maps/tables. Actions still need
on-screen approval; the voice says so and waits.

Uses the browser's Web Speech API (`frontend/client/src/lib/voice.ts`): free, no
server. **Chrome/Edge send the audio to the browser vendor's speech service; Safari
uses Apple's.** Firefox has no speech recognition (the mic button is disabled).
Voice quality depends on the voices installed on the device. Either half can be
replaced by a server-side speech provider later without changing the panel.

Verified in the browser with a simulated microphone and speaker (no real audio):
listening (live transcript) → thinking → speaking two short sentences → listening
again → paused on silence; Arabic toggle switches recognition to `ar-SY`.
Then tried by the owner with a real microphone in the browser (2026-11-20): works.

### In the Expo app

- **Floating button on every signed-in screen** (`expo_app/components/assistant/AssistantFab.tsx`):
  drag it anywhere to uncover what's under it; it snaps to the nearest side and
  remembers its spot across screens and launches. Hidden on login/signup, on the
  assistant screen itself, when signed out, and when the build has no `ASSISTANT_URL`.
- **Tap → the assistant screen** (`expo_app/app/assistant.tsx`), pushed on top of the
  current screen: back (header arrow, swipe, Android back button) pops only it, so
  you return to exactly where you were, scroll position included.
- Type or talk; answers stream in; charts reuse the app's own svg charts, maps use
  react-native-maps (pins, heat, routes), approvals are cards (CONFIRM for money/
  stock/deletes). **The same conversation as the web panel** (same user, same service).
- Voice uses the phone's own speech services: `expo-speech-recognition` (iOS Speech
  framework / Android SpeechRecognizer) and `expo-speech`. Same loop as the web:
  listen → answer spoken sentence by sentence → listen; `EN / عربي`; "One moment…".
  **These are native modules: the app needs a new build** (dev client / EAS), and the
  build now asks for microphone + speech-recognition permission (Android:
  `RECORD_AUDIO`; Google Play will want that declared).
- Configure: `ASSISTANT_URL` (and `API_BASE_URL`) at build time — `app.config.ts`.

### History

Each user has one conversation per company, kept until they press "Clear history"
(the ↺ button). It survives page changes (the widget is mounted once at the app
root), reloads, closed tabs, sign-outs and service restarts. The service stores
both what the panel shows (answers, charts, approval cards and their outcome) and
the model's memory, so follow-up questions work after a reload. A platform owner
impersonating a company gets a separate history for that company. If a page is
reloaded mid-answer, the answer still finishes and is saved (an open approval is
cancelled, since nobody can answer it); the panel polls until it is done.

Spike storage: `backend/assistant/data/assistant.sqlite3` (gitignored, override
with `ASSISTANT_DB`). Production: a tenant-scoped table in Karma's Postgres.

### Charts

The assistant can draw a chart in the chat with `show_chart` (bar, horizontal bar,
stacked bar, line, area, pie), rendered live with recharts in the widget and as a
text bar chart in the terminal. Charts can be anything, not just existing
dashboards. With a `query` source the service runs the query as the user and plots
exactly what Karma returns; numbers the model supplies itself are allowed only for
combined results and are labelled "Figures combined by the assistant". Dates can be
bucketed (`created_at:month`, `:week`, `:quarter`…) in `query_data` and charts.
Tested: "monthly payments collected in SYP and USD since July" (two charts, checked
against the raw payments) and "top 8 customers by SYP debt" (horizontal bar).

**Heatmaps** (`show_chart` type `heatmap`): a two-dimensional grid, e.g. weekday ×
hour of payments or material × month of sales. Date buckets include `:weekday`
(Mon..Sun) and `:hour` (00:00..23:00), computed in the business's local time
(`ASSISTANT_TZ`, default `Asia/Damascus`).

**Maps** (`show_map`, Leaflet + OpenStreetMap like the app's other maps):
pins (one per record, coloured by a group field, sized by a value, with a tooltip),
a density heat grid (weighted by a value such as debt, or by record count, computed
by the service — no Leaflet plugin), and GPS routes (a trip's track, or a driver's
over a time window) with start/end markers. Records come from a query the service
runs as the user; records without coordinates are counted and reported.

### Analysis toolkit (`joins.py`, `geo.py`, `toolkit.py`)

Deterministic helpers so the model never stitches tables together itself.
The full question checklist with coverage is in `CAPABILITIES.md`.
- `query_data` **joins** (applied in order, also usable in `show_map` and
  `compare_periods` queries): lookup (`order.customer_uuid → customer`), the virtual
  `users` dataset (names for any `created_by_uuid`), one-to-many summaries
  (`customer → its orders: count, last date…`), and **spatial joins** to service areas
  (point-in-polygon on Karma's WKT polygons, holes and multipolygons handled).
- **compute**: add/sub/mul/div/pct, `days_since`, `days_between`, `distance_km`
  (haversine), concat, coalesce — no model-written code runs.
- **having**: filter after grouping.
- Helpers (deferred tools, found via tool search): `list_users`, `ar_aging`,
  `customer_statement` (with a check against Karma's own balance), `stock_position`
  (days of cover; flags negative stock), `compare_periods` (presets or explicit
  windows), `trip_metrics` (GPS km with glitch filtering, pace, outcomes).

### Speed (measured 2026-11-20, local data, Opus 5.5)

Each answer now logs model vs tool time (assistant service console; `timing` in the
`done` event and in eval results). About 90% of the wait is the model: 2–3 calls per
answer at ~3–6 s each; fetching data is 0.2–1.8 s per list.

Free changes made: per-conversation list cache (2 min, cleared on every write),
pages fetched 4 at a time, prompt asks for independent lookups in one turn, and in
voice mode a short "One moment…" if nothing has been said after 1.2 s.

Effort A/B, interleaved, 9 eval questions that completed in both arms (the API
credit ran out before the last 3):

| Effort | Passed | Median | Mean | Slowest | Model calls/q | Cost |
|---|---|---|---|---|---|---|
| medium (current) | 9/9 | 9.5 s | 10.0 s | 14.2 s | 2.4 | $0.28 |
| low | 9/9 | 7.7 s | 7.5 s | 9.0 s | 2.1 | $0.14 |

Low was faster on 6 of 9 questions (up to 6.5 s), equal on 2, 1.2 s slower on 1.

**Applied: spoken questions run at low effort, typed ones at the model's default
(medium)** — `ASSISTANT_VOICE_EFFORT` changes it. Decided per question. Note: the effort
is a request-level setting, so switching between voice and typing in a long
conversation re-writes its prompt cache once per switch.
Quality held on these simple questions; multi-step questions (joins, maps, actions)
were **not** tested at low effort. Small sample: a direction, not a guarantee.

### Cost of long conversations

Every model call re-sends the whole conversation, so long chats get expensive.
Measured on a real 39-message conversation (count_tokens): 71K input tokens per call
before, 29K after (8K of that is the fixed prompt + tool definitions). What does it:
- **Server-side clearing of old tool results** (`clear_tool_uses_20250919`, beta
  `context-management-2025-06-27`): past 20K tokens the API replaces older tool
  results with a placeholder, keeps the last 4, clears ≥8K at a time so the cache
  isn't rebuilt every call; chart/map/tool-search results are never cleared. Applied
  per request — the stored history stays complete and saved reasoning stays valid.
- **1-hour prompt cache** instead of 5 minutes: a pause between questions no longer
  re-writes the whole conversation. (1h writes cost 2× input; re-reads 0.05×.)
- **Leaner tool results**: no nulls / `is_deleted: false`, compact JSON, 12K-char cap.
- **Endpoint list sent once** (in `query_data`), not repeated in chart and map tools.

In the browser: a follow-up question in that long conversation went from **$0.35
to $0.031**. The first question after the service restarts, or after more than an
hour idle, still pays a one-time cache write (~$0.25 for that conversation).

### Keeping saved conversations valid

Claude ties its saved reasoning to the exact system prompt, tool list and earlier
messages. Saved conversations outlive all three (deploys change prompts and tools;
permission changes change a user's tool list), so:
- the top-level system prompt never varies per user or per day; the "who / today"
  context is appended as a system message only when it changes;
- every request sends `thinking.block_binding.prefix_mismatch_behavior: "drop_block"`
  (beta `thinking-binding-controls-2026-08-01`): outdated reasoning blocks are
  dropped instead of the request failing. The visible conversation is unaffected.

Then open http://localhost:3001 and sign in. The service validates the user's
JWT with `/auth/me`, binds each conversation to that user, and keeps
conversations in memory (lost on restart; 2 h idle expiry).

## Run it in the terminal (local stack only)

Prerequisites: the local stack is up (`docker compose -f docker-compose.local.yml up`),
`uv` is installed, and your Anthropic API key is in your shell (never commit it).

```bash
cd backend
export ANTHROPIC_API_KEY=...        # your key
export KARMA_PASSWORD=...           # the local user's password
uv run --no-project --python 3.12 --with-requirements assistant/requirements.txt \
    python -m assistant.cli --username admin
```

Flags: `--model anthropic:claude-opus-5-5` (default), `--effort low|medium|high`,
`--code` (programmatic tool calling), `-q "question"` for one shot. The CLI refuses
any non-localhost API.

Each answer ends with a line like
`[4 model calls · 3 tool calls · 2100+18000c in / 900 out · $0.041 · 12.3s · end_turn]`.

## Eval

```bash
uv run --no-project --python 3.12 --with-requirements assistant/requirements.txt \
    python -m assistant.eval.run --username admin            # add --code to compare
```

12 starter questions (English + Arabic: counts, debt rankings, unpaid totals, tags,
trips, relative dates). Ground truth is computed from the API at run time; an answer
passes when it contains every expected number (±1%) and name. Results go to
`assistant/eval/results/` (gitignored). Costs real money: ~$0.05–0.50 per question.

Replace the starter set with your users' real questions — that set decides which
models get enabled.

### Results so far (2026-11-20, local data, Claude Opus 5.5, effort medium, no `--code`)

| Run | Result | Cost | Time |
|---|---|---|---|
| Starter eval, 12 questions (EN + AR) | **12/12 passed** | $0.26 total, **$0.022/question** | 9.7 s/question |
| "Top 3 USD debtors" (CLI) | correct, matches API | $0.045 | 13 s |
| Trip by name → sales, cash per currency, skipped stops (needed tool search → `trip__get_trip_activity`) | correct, reconciled stock and expenses | $0.061 | 17 s |
| Top 5 SYP debtors not visited in 30 days (balances × last stop) | correct | $0.052 | 22 s |

Most answers use `query_data` (1–4 calls); prompt caching makes ~95% of input
tokens cache reads. Answers lead with the result, keep currencies separate, and
reply in Arabic when asked in Arabic.

Data observation from the eval (not an assistant issue): some SYP invoices with
partial payments still have status `pending` rather than `partially_paid`.

## Known limits of the spike

- Confirmations are terminal prompts; the app version renders them as cards.
- One write per confirmation (no "approve all" for multi-step tasks yet).
- CLI only; no service, streaming endpoint, conversation storage or UI yet.
- `--code` (programmatic tool calling) runs in Anthropic's code-execution container:
  data there is retained up to 30 days and it is not zero-data-retention eligible.
- Many list endpoints filter on equality only (no date ranges); `query_data` filters
  locally after fetching, capped at 5,000 rows by default (20,000 max).
- 61 read endpoints have no docstring, so their tool descriptions are generic.
